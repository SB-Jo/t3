## 9쪽 — HOW IT WORKS / Weave는 어떻게 기억을 엮을까요?

구현 파이프라인 — Weave는 어떻게 기억을 엮을까요? 찾은 기록이 다음 단서가 되어, 기억나지 않던 답까지 이어집니다.

[왜 연쇄 탐색인가] Weave가 받는 요청은 키워드 검색보다 불완전합니다. "지은이네 집들이 때 마신 와인"을 찾는 사용자는 제품명도 날짜도 모르고, 답이 담긴 사진에는 '지은'이나 '집들이'라는 글자가 없을 수 있습니다. 그래서 질문과 정답을 바로 비교하기보다, 답까지 이어 줄 중간 근거를 찾는 능력이 중요합니다.

[00 사전 준비] 평소에는 사용자가 허용한 기록만 기기 안에서 정리합니다. 사람·시간·장소 정보와 사진 속 글자를 뽑아 키워드 색인과 벡터 색인으로 만들어 둡니다. 무거운 작업은 충전·유휴 시간에 하고, 이후에는 바뀐 기록만 갱신합니다. 개인 기록으로 모델을 다시 학습시키는 것이 아니라 검색용 색인을 만드는 것입니다.

[01 순간 감지] 사용자가 직접 부르거나(검색창 입력, Weave 버튼), 대화 맥락을 파악한 뒤 조건을 감지하면 시작합니다. 먼저 건넬 때는 관련이 있는지, 지금 쓸 수 있는지, 최근에 알렸는지를 한 번 더 확인합니다.

[02 단서 정리] 탐색 메모에 찾을 것(와인 이름)과 아는 단서(지은·집들이)를 나누고, 먼저 볼 곳(캘린더)을 정합니다. 캘린더에서 확인한 날짜(3/15 18:00)는 새 단서로 메모에 더해지고, 이 메모를 보고 다음에 무엇을 찾을지, 언제 멈출지 정합니다. 검색 결과를 질문 뒤에 계속 붙이는 방식보다 같은 기록을 반복하거나 엉뚱한 방향으로 흐를 위험이 적습니다.

[03 연쇄 탐색] 찾은 단서가 다음 검색의 조건이 됩니다. 단계별 태그처럼, 흐릿한 단서("집들이")로 캘린더의 '지은 집들이' 일정 — 정답은 없지만 답으로 이어지는 중간 근거 — 를 찾는 부분이 Reasoning Embedding의 추론 검색입니다. 날짜를 확인한 뒤로는 정확한 조건이므로 시간 필터로 사진을 좁히고, 라벨은 OCR로 읽습니다. Reasoning Embedding의 가치는 이름을 모르거나 표현이 달라도 관련 기록을 찾고, 지금 단서에 비춰 도움이 될 다음 기록을 고르고, 겉보기엔 비슷하지만 다른 사람·다른 행사의 기록을 가려내는 데 있습니다. 날짜·출처처럼 정확히 알 수 있는 것은 추론하지 않습니다.

[04 전달] "골라서, 직접 완성해 볼까?" — 후보를 출처와 함께 보여주고, 사용자가 출처를 확인한 뒤 고른 것만 직접 입력해 문장·검색어를 완성합니다. 자동으로 보내거나 바꾸지 않습니다. 먼저 알리는 기억은 근거가 확실할 때만 표시합니다.

[종료 조건] 필요한 정보가 채워지면 멈춥니다. 새 단서가 없거나 탐색 한도에 닿아도 멈춥니다. 후보가 여럿 남으면 하나를 임의로 확정하지 않고 사용자에게 고르게 합니다.

[핵심] 핵심 엔진은 온디바이스 Reasoning Embedding으로, 지금 단서로부터 '이어지는' 기록을 찾는 경량 모델입니다. 긴 추론 문장을 매번 생성하지 않고도 현재 단서에서 다음 근거를 찾고, 탐색 메모가 단서의 연결과 종료를 관리합니다. sLLM은 복잡한 요청 해석과 문장 구성에만 씁니다.

(참고) 모델 크기·탐색 횟수·후보 수는 제안 설계의 시작값이며, 최종 모델은 한국어 개인 기록으로 비교해 정합니다.

## 10쪽 — WHY SAMSUNG / 기록은 자유롭게, 기억은 단 한 곳에서

왜 삼성인가 — 서드파티의 한계를 넘는 시스템 레벨의 통합 경험. ① 독보적인 앱 생태계: 특정 플랫폼 앱은 자사 서비스 내부의 데이터만 볼 수 있지만, 삼성은 갤러리·삼성노트·캘린더처럼 기록이 쌓이는 기본 앱과 이를 다시 꺼내 쓰는 삼성 키보드를 하나의 제품 경험으로 설계할 수 있습니다. ② 크로스 앱 데이터 융합: 앱 사이의 벽을 허물고 디바이스 전체에 흩어진 단서를 하나의 실처럼 엮어, 사용자가 별도의 앱을 켜지 않고도 매일 쓰는 키보드 안에서 필요한 기억을 바로 활용하게 합니다. ③ 완전한 온디바이스 보안: Personal Data Engine 기반으로 개인 데이터를 기기 안에서만 처리하고, KEEP·Knox Vault와 연계해 기록이 외부 서버로 나가지 않도록 보호합니다.

## 11쪽 — WHY NOW / 왜 지금인가

왜 지금인가 — 기기 안에서 기록을 이해하고 실제 사용으로 연결할 온디바이스 AI 인프라가 갖춰지고 있습니다. 갤러리·삼성노트·캘린더에 남은 기록을, 온디바이스 API(Android AICore), 모바일용 경량 LLM(Gemini Nano, Llama), 그리고 AI 연산 특화 하드웨어인 NPU가 기기 안에서 이해하고, Weave가 이를 찾아 지금의 입력에 연결합니다. Weave는 기록을 더 많이 저장하는 것보다, 이미 남아 있는 기록을 필요한 순간 꺼내 쓰는 과정에 집중합니다.

## 12쪽 — 차별화 포인트 / 기능 중심의 AI를 넘어, 나의 맥락을 잇는 'Contextual AI'로

경쟁 서비스 비교 — Samsung Writing Assist는 입력 중인 문장을 생성·교정하는 도구, Now Nudge는 상황을 인지해 정보를 안내하는 서비스, Kanana는 카카오톡이라는 단일 앱 안에서 동작합니다. Weave는 갤러리·삼성노트·캘린더·문자 등 기기 전체에 흩어진 기록을 연결하고, 컨텍스트를 기반으로 앱을 넘나들며 연쇄 탐색하고, 데이터를 온디바이스로 처리하며, 입력창에 진입하는 순간 연관 맥락을 키보드에 먼저 띄운다는 점에서 차별화됩니다.

- Android Keystore: 암호화 키를 기기에서 추출하기 어렵게 보관, 키 자료는 내보낼 수 없음.
- 추가 질문 대비: 공개 ML Kit GenAI API는 최상위 포그라운드 앱에서만 추론을 허용합니다(백그라운드 사용 시 BACKGROUND_USE_BLOCKED). 키보드·백그라운드 UX는 자체 모바일 런타임이나 삼성 내부 연동 경로로 검토한다고 답합니다.
- Q3 보충 끝 문장: "후보와 원문을 먼저 보여주어, 최종 판단은 사용자가 내리도록 합니다."
- KEEP·PDE: 삼성 공식 자료는 PDE 인사이트가 기기 안에 머물고 KEEP·Knox Vault로 보호된다고 설명하지만, 외부 앱용 API는 언급하지 않습니다. '연계를 검토한다'로 답합니다.

## 18쪽 — Appendix · Q&A / (Reasoning) Embedding Model이란?

Appendix · Q&A — (Reasoning) Embedding Model이란? (2026-09-27 원문 확인)

Q1 임베딩: 글과 사진의 의미를 벡터로 바꿔, 가까운 것을 관련 기록으로 찾습니다. 기록 벡터는 미리 저장하고 검색 때는 질문도 벡터로 바꿉니다. 정확한 이름은 키워드 색인, 표현이 다른 내용은 벡터 색인으로 함께 찾습니다.

Q2 왜 LLM이 아닌가: LLM은 출력 토큰마다 계산을 반복하며 글을 생성하고, 임베딩은 입력당 한 번 계산해 벡터 하나를 냅니다(일반 원리). 휴대폰은 메모리·전력이 제한적이라 문장 생성은 꼭 필요할 때만 쓰고, 기록 벡터는 충전·유휴 시간에 미리 만들어 둡니다. (추가 질문 대비) LaSER 같은 추론형 임베딩은 긴 문장을 생성하지 않는 대신 짧은 내부 계산(잠재 추론)을 몇 단계 더하므로, 엄밀히는 일반 임베딩보다 조금 더 계산합니다(논문 기준 일반 검색기 대비 약 1.7배, 서버 GPU 측정).

Q3 왜 Weave에 필요한가: Weave의 요청은 제품명·날짜를 모르는 등 일반 검색보다 불완전하므로, 답까지 이어 줄 중간 근거(예: 집들이 일정)를 찾는 능력이 중요합니다. 그래프는 BRIGHT(ICLR 2025) 초록의 수치로, 게재본 초록에서 직접 확인했습니다: SFR-Embedding-Mistral이 BEIR에서 59.0 nDCG@10, BRIGHT에서 18.3(질의 1,384개). 같은 모델을 서로 다른 벤치마크에서 잰 값이라 '왜 단순 검색만으로 어려운가'의 근거이며, Weave 성능 증거는 아닙니다. BRIGHT는 StackExchange·코딩·수학 문제로 개인 기록 데이터가 아닙니다. ReasonIR(COLM 2025)은 추론이 필요한 질문에 유용한 근거를 찾도록 검색 모델을 학습시키는 연구입니다. (추가 질문 대비) '일반 임베딩은 비슷한 말'이라는 대비는 설명을 위한 단순화입니다. 일반 검색용 임베딩도 질문에 유용한 문서를 찾도록 학습되며, 차이는 조건과 관계를 풀어야 하는 경우를 더 잘 다루도록 학습한다는 점입니다.

Q4 연쇄 탐색: 찾은 기록의 단서를 탐색 메모에 더하고, 메모의 찾을 것·확인한 단서·아직 필요한 정보로 다음 근거를 찾습니다. 날짜 같은 정확한 조건은 필터로 좁히고, 필요한 정보가 채워지거나 새 단서가 없거나 탐색 한도에 닿으면 멈춥니다. MDR(Xiong et al., ICLR 2021): "we simply concatenate the question and the retrieved passages as the inputs to g(·)" — 질문과 앞서 찾은 문서를 함께 인코딩해 다음 문서를 찾으며, 텍스트 생성이나 문서 간 하이퍼링크가 필요 없습니다. 학습 데이터는 '질문 + 확인한 단서 → 다음 근거' 쌍과 헷갈리기 쉬운 오답으로 구성합니다. 헷갈리는 오답(hard negative)을 함께 만드는 방식은 ReasonIR 초록의 "for each document, our pipeline creates a challenging and relevant query, along with a plausibly related but ultimately unhelpful hard negative"를 근거로 ²를 달았습니다. 07번 장표의 메모 표기(찾을 것 / 아는 단서 / 먼저 볼 곳 / + 새 단서)는 이 세 항목을 와인 예시로 풀어 쓴 것입니다.

(참고) IRCoT(ACL 2023)는 LLM의 추론 문장과 검색을 번갈아 하는 일반 원리입니다. Weave 방식의 성능 근거가 아니어서 장표에는 MDR만 인용했습니다.
