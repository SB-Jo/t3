## 2. 번역 범위

- **필수**: 초록 + 본문(부록 제외)의 모든 `h2·h3·h4·p·li·fn` 블록, 그리고 `fig·tab·alg` 블록의 캡션(`html`이 비어 있지 않은 것).
- **부록**(`appendix: true`): 절 제목과, 방법·파이프라인·구현을 설명하는 문단만 번역한다(예: 알고리즘 설명, 인덱싱·검색 세부, 학습 데이터 구성). 긴 프롬프트 원문, 추가 실험 표 나열, 사례 덤프는 건너뛴다. 무엇을 건너뛰었는지 보고한다.
- `eq`(수식 블록)와 표 본문(`table`), 알고리즘 줄(`lines`)은 번역하지 않는다.

## 3. 번역 규칙

- 원문을 **빠짐없이 문장 단위로** 옮긴다. 요약·의역·생략 금지. 원문의 수치·조건·단서("on average", "up to", "in the oracle setting")를 그대로 살린다.
- 문체: 한국어 학술 문어체(~다). 자연스러운 어순으로 쓰되 의미를 바꾸지 않는다.
- 용어: 처음 나올 때 `한국어(English)`로 쓰고, 이후에는 한국 ML 커뮤니티에서 흔히 쓰는 쪽을 쓴다. 예) 다중 홉(multi-hop) 질의응답, 검색기(retriever), 밀집 검색(dense retrieval), 재순위화(reranking), 하드 네거티브(hard negative), 지식 그래프(knowledge graph), 개인화 페이지랭크(Personalized PageRank, PPR), 사고의 사슬(chain-of-thought, CoT).
- 모델·데이터셋·지표 이름은 영어 그대로: HotpotQA, 2WikiMultiHopQA, MuSiQue, GPT-4, Contriever, ColBERTv2, nDCG@10, Recall@k, EM, F1.
- `Figure 2` → `그림 2`, `Table 1` → `표 1`, `Section 3`/`§3` → `3절`, `Appendix A` → `부록 A`, `Eq. (1)` → `식 (1)`.
- **html 안의 표시는 그대로 보존**한다.
  - 수식 `\( … \)`, `\[ … \]`는 글자 하나 바꾸지 말고 그대로 복사한다.
  - 인용 `<span class="cite">…</span>`은 통째로 그대로 둔다(안의 저자명도 번역하지 않음).
  - `<b>`, `<i>`, `<code>`, `<sup class="fnm">n</sup>`, `<a href=…>`는 대응하는 한국어 구절에 그대로 씌운다(개수 유지).
- 절 제목은 번호를 유지한다: `3.2 Query Refinement` → `3.2 질의 정제(Query Refinement)`.

## 4. 번역 파일 쓰기

- `work/<key>/ko/part_01.json`, `part_02.json`, … 에 나눠 쓴다. 각 파일은 `{"b012": "한국어 html", "b013": "…"}` 형태의 JSON 객체 하나다. 한 파일에 블록 25~40개 정도로 나눈다(너무 큰 Write는 피한다).
- JSON 문자열 안의 큰따옴표는 `\"`로, 역슬래시는 `\\`로 이스케이프해야 한다(수식의 `\(`는 JSON에서 `\\(`). 파이썬으로 쓰는 편이 안전하면 `json.dump(..., ensure_ascii=False)`를 써도 된다.
- 다 쓰면 검사한다:


  `OK`가 나올 때까지(빠진 id 0) 고친다. 경고(수식·태그 개수)는 하나씩 확인해 원문과 맞춘다.

- `results`의 수치는 **반드시 원문 문장을 그대로 인용**한다(본문·표에서 직접 확인). 추론하거나 계산한 값을 논문 주장처럼 쓰지 않는다. 계산한 값이면 "(제 계산)"을 붙인다.
- `weave`는 과장하지 않는다. 이 논문의 성능을 Weave의 성능처럼 쓰지 않는다.
- Weave 배경(설계 요약): 사용자가 허용한 기기 안의 기록(카톡·캘린더·사진·노트·위치 등)을 미리 사람·시간·장소·사진 속 글자로 정리해 키워드+벡터 색인을 만든다. 요청(검색어, 버튼, 대화·위치 맥락)이 오면 '탐색 메모'(찾을 것 / 아는 단서 / 먼저 볼 곳 / + 새 단서)를 만들고, 온디바이스 경량 Reasoning Embedding이 "지금 단서에서 이어지는" 다음 기록을 찾는다. 찾은 단서가 메모에 더해져 다음 검색 조건이 되고(멀티홉), 날짜 같은 정확한 조건은 필터로, 사진 속 글자는 OCR로 처리한다. 필요한 정보가 채워지거나 새 단서가 없으면 멈추고, 출처와 함께 추천 문장·검색어로 건넨다. 매 홉마다 긴 추론 문장을 생성하지 않는 것이 목표이고, sLLM은 복잡한 요청 해석과 문장 구성에만 쓴다. 예시 시나리오(How it Works 장표의 중심): "지은이네 집들이 때 마신 화이트 와인, 이름이 뭐였지?" → 캘린더에는 일정이 없고, 지은이 3/12(수)에 보낸 카톡 "이번 주 토요일 6시, 이사 기념으로 우리 집에서 저녁 먹자!"가 중간 근거('집들이'라는 단어가 없어 뜻으로만 이어짐, 추론 검색) → 새 단서 3/15(토) 18시 이후(시간 필터) → 그날 저녁 사진 두 장(레드 CABERNET SAUVIGNON, 화이트 BABICH SAUVIGNON BLANC) → 라벨 OCR + '소비뇽 블랑 = 화이트' 추론 → '배비치 소비뇽 블랑'을 출처와 함께 건넴. 방해 기록: '집들이 선물 와인 BEST 5' 캡처, '화이트 와인 추천 리스트' 노트, '[쿠팡] 와인잔' 메일, '회식은 와인바 어때요?' 카톡. **무화과시루(대전역·엄마) 시나리오는 덱에서 빠졌으니 쓰지 말 것.**
