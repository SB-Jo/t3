# '탐색 메모' 대신 '질문 다시 쓰기' — 기술 근거 (2026-11-01)

## 결론

멀티홉 검색 연구는 모두 **앞에서 찾은 것을 다음 질의에 넣은 뒤** 다시 검색한다. 방법만 다르다.

- 글로 다시 쓰기: Hi-Q, IRCoT
- 작은 분류기로 다음 질의 조립: EfficientRAG
- 질문과 찾은 문단을 이어 붙여 다시 인코딩: MDR

그래서 How it Works의 02단계를 '탐색 메모'(찾을 것, 아는 단서, 먼저 볼 곳, 새 단서, 멈출 때)에서 **'질문 다시 쓰기'**로 바꿨다. 장표3의 8개 판이 모두 이 흐름을 따른다.

1. 한 번에 안 찾아지는 질문을 '먼저 풀 질문'과 '그 답이 들어갈 질문'으로 나눈다. 빈자리는 '그날', '그때', '그것'처럼 남겨 둔다.
2. 먼저 풀 질문을 Reasoning Embedding으로 찾는다.
3. 찾은 단서로 다음 질문의 빈자리를 채워 다시 쓴다. 예: [그날 → 3/15 (일) 저녁] 마신 화이트 와인은?
4. 다시 쓴 질문에서 날짜·시간처럼 정확한 조건은 필터로 빼고, 나머지 뜻은 Reasoning Embedding으로 찾는다.
5. 답이 나오면 멈춘다.

## 논문별 근거

모두 `논문스터디/work/<논문>/src.txt` 원문에서 확인한 문장이다.

### Hi-Q (NeurIPS 2026) — 다시 쓰기를 검색보다 먼저

- 노드마다 '정제(다시 쓰기) → 검색 → 답하기'를 한다. §3.2, b040 원문:
  > "Refinement rewrites the current query from the accumulated history ℋ while keeping it anchored to the original question Q, and it has to precede retrieval because dependent sub-queries often contain references whose meaning is fixed only by earlier steps."
- 예: 'the performer of III'를 Stanton Moore로 바꿔 쓴 뒤 검색한다(그림 2, 프로젝트 페이지 GIF의 `[the performer → Stanton Moore]`). 장표의 `[그날 → 3/15 (일) 저녁]` 표기가 여기서 왔다.
- 답이 안 나오면 둘로 나눈다. §3.3, b143 원문:
  > "q_left, which resolves the bridge fact, and q_right, which uses that bridge to approach the parent query's answer"
- 효과 근거. 다른 연구진의 위키백과 QA 결과이며 Weave 성능이 아니다.
  - 의존성 인지를 빼면 통제 설정 평균이 57.9 → 47.1 EM으로 떨어진다(§4.4, 표 6). 이유는 "dependent sub-queries can become under-specified when issued before prerequisite facts are resolved"이다.
  - 분해가 트리거된 MuSiQue 사례(Clean)에서, 같은 top-5 예산으로 필요한 정답 문단을 모두 찾은 비율이 원래 질문 7.9%에서 나눈 질문 42.7%로 오른다(§4.3, 표 3).
- 주의(대비):
  - Hi-Q는 다시 쓰기, 답하기, 분해, 검증을 모두 GPT-4o-mini로 한다. 질문당 LLM 호출은 평균 5.7회다(표 8).
  - Weave를 'Hi-Q 방식'이라고 소개하거나 이 비용·성능 수치를 Weave에 붙이면 안 된다.

### EfficientRAG (EMNLP 2024) — 홉마다 LLM 없이 다음 질의

- 초록 원문:
  > "EfficientRAG iteratively generates new queries without the need for LLM calls at each iteration"
- 그림 3: "Q: How large is the shopping mall where KGOT radio station has its studios? Info: KGOT, in the Dimond Center"에서 다음 홉 질의 "How large is Dimond Center?"를 만든다. 질문 속 빈자리를 찾은 단서로 바꾸는 모양이 장표와 같다.
- 주의:
  - 두 분류기는 각각 DeBERTa-v3-large(백본 304M)다.
  - 질문과 문단의 단어를 고르는 추출식이라, 날짜 정규화나 사진 속 글자는 다루지 않는다.

### MDR (ICLR 2021) — 생성 없이 '질문 + 찾은 것'을 다시 인코딩

- §2.2 원문:
  > "we simply concatenate the question and the retrieved passages as the inputs to g(·)"
- 장표의 '다시 쓴 질문'을 글이 아니라 벡터 수준에서 하는 가장 가벼운 선례다.

### IRCoT (ACL 2023) — 왜 다시 써야 하나

- 초록 원문:
  > "what to retrieve depends on what has already been derived, which in turn may depend on what was previously retrieved"

### LaSER — 다시 쓰기 대신 잠재 추론

- 초록 원문: 기존 방식은 "rewrite-then-retrieve" 파이프라인으로 명시적 추론을 생성한다.
- LaSER는 생성 없이 잠재 단계로 그 성능에 가깝게 간다고 보고한다.
- 정리하면 두 가지가 서로 다른 일을 한다.
  - 멀티홉에서 앞 홉의 답을 다음 질문에 넣는 일은 '질문 다시 쓰기'가 한다.
  - 한 홉 안에서 '휴지 안 사 와도 돼 = 집들이 초대'처럼 말 밖의 상식으로 잇는 추론은 Reasoning Embedding이 한다(2026-11-05 시나리오).

### LongMemEval (ICLR 2025) — 날짜는 필터로

- §5.4 원문:
  > "a simple indexing and query expansion strategy to explicitly associate timestamps with facts and narrow down the search range"
- 강한 LLM으로 질의를 확장하면 시간 추론 재현율이 6.8~11.3% 오른다고 보고한다.
- 장표에서 다시 쓴 질문의 날짜를 필터로 빼는 근거다.

   > "질문을 작은 질문으로 나누고, 찾은 기록의 단서로 다음 질문의 빈자리를 채워 다시 씁니다. 다시 쓴 질문을 Reasoning Embedding이 숫자로 바꿔, 이어지는 기록을 찾습니다. 날짜처럼 정확한 조건은 필터로 따로 거릅니다."

## 4차(2026-11-01 오후): 시나리오를 멀티홉 위주로, '00 사전 준비' 빼기

사용자 피드백에 따라 장표4(`../장표4/`)로 다시 만들었다.

- **단서가 비어 있는 멀티홉을 중심으로 한다.** 처음 질문엔 답으로 가는 단서가 없고, 중간 기록에서 찾은 단서로 다음 질문의 빈칸을 채워야 답에 닿는다.
- **추론은 조금만 쓴다.** '소비뇽 블랑 = 화이트 와인', '목요일 같은 상대 날짜 계산', 'minji_k = 민지', '언니 = 처형', '잡은 곳 = 예약한 곳' 정도다. 숨은 조건이나 이유를 짐작하는 시나리오(무릎 → 좌식 안 됨 등)는 쓰지 않는다.
- **다리(bridge)는 되도록 기록의 내용에서 나온다.**
  - A2 '민지 인스타 속 고기국수집', B1 '민수 님이 맡은 반품 현황', B2 '준호가 잡은 곳', C1 '참기름', C2 '오타니 유니폼', C3 '언니가 쓰는 갈색병'이 그렇다.
  - A1은 날짜가 다리이고, 날짜는 필터가 맡는다.
  - B2의 2홉은 사실상 '보낸 사람 = 준호'로 이어지므로 그래프로도 된다. Q&A에서 숨기지 않는다.
- 파이프라인에서 '00 사전 준비'(데이터 전처리)를 뺐다. 01 순간 감지 → 02 질문 다시 쓰기 → 03 연쇄 탐색 → 04 전달.

### 예상 질문: "날짜나 관계로 잇는 건 지식 그래프로 되지 않나요?"

맞는 지적이다. 지식 그래프로 멀티홉 검색을 하는 연구(HippoRAG)도 있다. 그래프는 날짜, 사람, 이름처럼 같은 값으로 이어지는 기록에 강하다.

- **HippoRAG도 비슷한 말끼리 미리 잇는다.** 인코더로 "between similar but not identical noun phrases"에 유사도 0.8 넘는 연결을 더한다(§3, L58). 그러니 "그래프는 못 긋는다"고 하면 안 된다.
- **그래도 미리 그어 두면 놓치기 쉽다.** 그래프는 질문을 모른 채 기록마다 개체와 관계를 뽑아 둬야 한다. HippoRAG 스스로 "most errors made by our system are due to NER and OpenIE"라고 쓴다(§7, L235).

답변 제안(공정한 판):

> "날짜, 연락처처럼 같은 값으로 이어지는 기록은 그래프로도 되고, 저희도 기록 정보로 바로 거릅니다(장표의 '필터'). 기록마다 다르게 적힌 연결, 예를 들어 '내가 인스타에 올린 고기국수집'과 캡처 속 '#바당식당, 애월읍'은 새 기록마다 관계를 뽑아 미리 이어 둬야 하는데, 그 추출에서 놓치기 쉽습니다. 폰은 기록이 계속 쌓이고 질문은 가끔이라, 저희는 질문이 생길 때 앞에서 찾은 단서로 질문을 다시 써서 뜻으로 이어지는 기록을 찾습니다. 그래프를 대체하기보다 보완하는 방식입니다."

- 숫자는 붙이지 않는다.
- 장표 본문에는 '지식 그래프' 비교 단계를 넣지 않는다(사용자가 '관계로 찾기' 비교를 빼라고 했음).

## 5차(같은 날 밤): 논문 9편 다시 읽고 고친 점

에이전트 셋이 논문을 나눠 다시 읽었고, 아래 인용은 원문(`../논문스터디/work/<논문>/src.txt`)에서 다시 확인했다.

### 장표의 비교 축: '한 번에 찾기' 대 '단서로 다시 쓰며 이어 찾기'

- Hi-Q 부록 G는 성능 향상이 "from evidence-guided query refinement rather than from a particular embedding model"에서 온다고 쓴다(L411).
- IRCoT의 향상도 키워드 검색(BM25, "as our base retriever", L131) 위에서 나왔다.
- 그래서 실패 장의 설명을 '비슷한 것을 한 번에 찾으면?'으로 바꾸고, 일반 임베딩 판에 '처음 질문 그대로, 한 번에'라고 적었다.
- Reasoning Embedding의 몫은 뜻으로 같은 일을 잇는 데('휴지 안 사 와도 돼' = 집들이, 잡은 곳 = 예약한 곳)로 좁혀 말한다. '블랑 = 화이트' 같은 말 바꾸기는 일반 임베딩도 할 수 있어서, Reasoning Embedding의 예로 내세우지 않는다(BRIGHT의 2단계 '의미 검색' 수준).

### 질문은 안 풀릴 때만 나눈다

- Hi-Q: "a query that single retrieval or a fixed graph already answers is never decomposed"(L22).
- ReasonIR: 한 번에 다 담긴 질문은 "an information-rich long query is better than several decomposed short queries"(L74).
- 그래서 장표는 '한 번에 안 되면, 질문을 나눠요'로 말한다. 앞의 답이 있어야 다음을 찾을 수 있는 질문만 나눈다.

### 한 홉에 기록 하나가 아니라, 가까운 기록 몇 개 중 근거 있는 것

- Hi-Q는 k=5, MDR은 빔 서치로 후보 여러 개를 가져온다.
- 장표의 '찾기' 장은 후보 실(옅은 점선)과 정답 실을 함께 보이고, '가까이' 장에서 후보에 이유 태그(예: '날짜가 없어요', '신발 사이즈예요')를 붙였다.

### 멈추는 규칙과 근거 원칙

- 모든 논문이 반복 횟수를 제한한다(IRCoT 최대 8단계, Hi-Q 깊이 4).
- 멈춤 장에 '끝까지 없으면 ‘못 찾았어요’라고 해요'를 붙였다.
- Hi-Q는 큰 모델이 찾지도 않은 다리 개체를 기억으로 채우는 사례를 보고한다(L447). 그래서 노트에 '빈칸에는 찾은 기록에 실제로 있는 내용만 넣는다'를 밝혔다.

### 날짜 필터

- LongMemEval §5.4: "extracts a time range for time-sensitive queries"(L244).
- 작은 모델은 시간 범위를 잘못 뽑아 검색 범위를 잘못 줄일 수 있다(L247, 부록 E.4). 그래서 노트에 '필터로 하나도 안 남으면 필터 없이 다시 찾는다'를 넣었다.

### 덱 부록(18쪽 Q&A)에 대한 제안(덱은 아직 안 고침)
